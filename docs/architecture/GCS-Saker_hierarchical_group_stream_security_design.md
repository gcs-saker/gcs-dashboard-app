# GCS-Saker 계층형 그룹 기반 스트림 보안 설계 의도

## 1. 목적

본 설계는 장비가 송출 목적지나 그룹을 직접 선택하지 않도록 하고, 서버가 관리하는 소속 그룹을 기준으로 스트림의 귀속과 조회·관리 권한을 결정하는 것을 목적으로 한다.

핵심 원칙은 다음과 같다.

> 클라이언트는 자신의 신원만 증명하고, 데이터의 귀속과 접근 범위는 서버가 결정한다.

## 2. 그룹의 의미

그룹은 화면상의 분류값이 아니라 다음 항목을 결정하는 보안 경계다.

- 장비와 사용자의 직접 소속
- 스트림 및 텔레메트리 데이터의 귀속
- Viewer의 조회 범위
- 관리자의 관리 범위
- 장비 제어 권한
- 감사 로그의 조직 범위

권한 판정에는 `co-a`와 같은 표시 이름이 아닌, 변경되지 않는 내부 `groupId`를 사용한다. 그룹 이름이나 계층상 표시 경로가 변경되어도 데이터 귀속과 권한 관계는 유지되어야 한다.

## 3. 장비 등록과 송출

장비는 등록 시점에 하나의 직접 소속 그룹을 부여받는다.

등록 원장은 최소한 다음 정보를 관리한다.

- 장비 UUID
- Credential
- 장비 표시 이름
- 직접 소속 `groupId`
- 장비 상태
- 등록된 센서 또는 카메라
- 서버가 허용한 스트림 경로

장비는 송출 시 `deviceUuid`와 `credential`만으로 자신의 신원을 증명한다. 장비가 다음 값을 지정하거나 선택해서는 안 된다.

- `groupId`
- `publisherGroupId`
- 송출 대상 그룹
- 서버 내부 종착지
- 사용자 입력 기반 스트림 ID

송출 흐름은 다음과 같다.

```text
송출 요청
→ UUID와 Credential 검증
→ 등록 장비 및 활성 상태 조회
→ 장비의 직접 소속 그룹 확인
→ 등록 센서 기준으로 스트림 식별자와 송출 세션 생성
→ 스트림을 장비의 직접 소속 그룹에 귀속
→ 제한된 송출 토큰과 송출 URL 발급
```

기술적으로 스트림 ID가 필요한 경우 서버가 등록 정보를 이용해 생성한다.

```text
raw.{deviceUuid}.{sensorId}
```

스트림 ID는 내부 식별자이며, 사용자가 송출 목적지로 입력하는 값이 아니다.

## 4. 데이터 귀속 불변식

하나의 장비 송출에서 다음 그룹 정보는 반드시 일치해야 한다.

```text
registered_device.group_id
= publisher_token.group_id
= stream_session.group_id
= telemetry.group_id
= event.group_id
```

`registered_device.group_id`를 귀속의 최종 원장으로 사용한다. 요청 URL, 스트림 이름, 브라우저 저장값 또는 클라이언트가 전달한 그룹 정보로 귀속 그룹을 추론하지 않는다.

장비의 직접 소속이 `co-a`라면 해당 장비의 스트림은 항상 `co-a`에 귀속되어야 한다. `co-b` 또는 다른 그룹으로의 송출은 클라이언트 조작 여부와 관계없이 서버에서 차단한다.

## 5. 사용자와 관리자 권한

Viewer와 관리자 역시 직접 소속 그룹과 역할을 가진다.

접근 허용 여부는 역할과 그룹 범위를 함께 검사한다.

```text
접근 허용
= 필요한 기능 권한 보유
AND 대상 그룹이 계정의 허용 범위에 포함
```

역할의 예시는 다음과 같다.

| 역할 | 기본 책임 |
|---|---|
| `publisher` | 등록 장비의 송출 수행 |
| `viewer` | 허용된 그룹 범위의 스트림 조회 |
| `operator` | 스트림 조회 및 허용된 장비 제어 |
| `group-admin` | 관리 범위 내 그룹·계정·장비 관리 |
| `system-admin` | 전체 조직 구조와 최상위 정책 관리 |

`admin` 역할만으로 모든 그룹 접근을 자동 허용하지 않는다. 관리자의 역할과 관리 가능한 그룹 범위를 항상 함께 검증한다.

## 6. 계층형 그룹

그룹은 상위·하위 관계를 가질 수 있다.

```text
co
├── co-a
│   ├── div-1
│   └── div-2
└── co-b
    └── div-3
```

장비와 사용자는 하나의 직접 소속 그룹을 가진다. 예를 들어 `div-1` 장비의 데이터는 `div-1`에 귀속하며, 조회 편의를 위해 `co-a`에 중복 귀속하거나 복제하지 않는다.

권한이 있는 상위 그룹 사용자는 하위 그룹의 스트림을 조회할 수 있다.

| 계정의 직접 소속 | 허용 가능한 조회 범위 |
|---|---|
| `co` | `co`와 전체 하위 그룹 |
| `co-a` | `co-a`, `div-1`, `div-2` |
| `div-1` | `div-1` |
| `co-b` | `co-b`, `div-3` |
| `div-3` | `div-3` |

기본 경계는 다음과 같다.

```text
co-a → div-1   허용 가능
div-1 → co-a   거부
div-1 → div-2  거부
co-a → co-b    거부
```

상위 그룹의 하위 그룹 조회는 계층만으로 무조건 허용하지 않고, `stream:view-descendants`와 같은 명시적 권한을 가진 역할에만 허용한다.

## 7. 그룹 관리 UI

관리자는 장비나 사용자를 등록할 때 그룹 이름을 텍스트로 직접 입력하지 않는다. 서버가 관리 가능한 그룹 목록을 반환하고, UI는 select-box 또는 계층형 선택기로 제공한다.

화면에는 `co-a > div-1`과 같은 경로를 표시할 수 있지만, 서버 요청에는 내부 `groupId`를 사용한다.

select-box는 입력 오류를 방지하기 위한 UI 장치일 뿐 보안 경계가 아니다. 서버는 모든 관리 요청에서 다음 조건을 재검증한다.

- 대상 그룹이 실제로 존재하는가
- 대상 그룹이 활성 상태인가
- 요청자가 해당 그룹을 관리할 권한이 있는가
- 대상 그룹이 요청자의 관리 가능한 계층 범위에 포함되는가
- 장비 또는 사용자를 해당 그룹으로 이동할 권한이 있는가

클라이언트가 임의의 `groupId`를 요청에 포함하더라도 권한 범위를 벗어나면 서버가 거부해야 한다.

## 8. 그룹 간 격리

서로 다른 형제 그룹은 기본적으로 격리된 보안 영역이다.

- `co-a` 장비의 스트림은 `co-a` 또는 그 직접 하위 그룹의 원장에만 귀속된다.
- `co-b` 장비의 스트림은 `co-b` 또는 그 직접 하위 그룹의 원장에만 귀속된다.
- `co-a` 사용자는 `co-b` 스트림을 조회할 수 없다.
- 하위 그룹은 상위 그룹 또는 형제 그룹의 스트림을 기본적으로 조회할 수 없다.
- 예외 접근은 소속 변경이 아닌 명시적 정책으로만 허용한다.

클라이언트가 다른 그룹의 이름이나 식별자를 알고 있어도 송출하거나 조회할 수 없어야 한다.

## 9. 서버 검증 요구사항

### 9.1 송출

- UUID와 Credential의 유효성
- 등록 장비의 활성 상태
- 장비의 직접 소속 그룹
- 요청 센서가 등록 장비에 허용되어 있는지 여부
- 서버가 발급한 스트림 제한 토큰

### 9.2 조회

- 사용자 세션 또는 Access Token의 유효성
- 역할별 스트림 조회 권한
- 사용자의 직접 소속 그룹
- 대상 그룹이 허용된 하위 범위에 속하는지 여부

### 9.3 관리

- 그룹 생성·변경 권한
- 관리 가능한 상위·하위 범위
- 순환 계층 발생 여부
- 그룹 이동에 따른 접근 범위 변화
- 장비와 계정의 재배치 권한

## 10. 송출 토큰 제한

서버가 발급하는 송출 토큰은 최소한 다음 범위에 결합한다.

- 장비 UUID
- 스트림 ID
- 센서 ID
- 서버가 결정한 그룹 ID
- `publish` 동작
- 만료 시간
- 서버 서명

토큰은 다른 장비, 스트림, 센서, 그룹 또는 동작에 재사용할 수 없어야 하며, 만료 이후에는 거부해야 한다.

## 11. 감사와 추적

다음 행위는 감사 로그로 남긴다.

- 그룹 생성·수정·이동·비활성화
- 장비와 사용자의 그룹 변경
- 송출 세션 생성·종료
- 다른 그룹에 대한 송출 또는 조회 거부
- 잘못된 Credential 사용
- 권한 밖의 `groupId` 지정 시도
- 예외 권한 부여와 회수

감사 로그에는 행위자, 행위자의 직접 소속 그룹, 대상 그룹, 대상 장비 또는 스트림, 판정 결과와 정책 버전을 기록한다.

## 12. 계층 관리 규칙

- 그룹 계층의 순환 관계를 금지한다.
- 최대 계층 깊이를 정책으로 제한한다.
- 그룹 삭제보다 비활성화를 우선한다.
- 하위 그룹이나 소속 장비가 있는 그룹은 즉시 삭제하지 않는다.
- 그룹 이동 전에 사용자와 장비의 접근 범위 변화를 계산한다.
- 그룹 이동 중인 장비의 활성 송출 처리 정책을 별도로 정의한다.
- 장비와 사용자는 기본적으로 하나의 직접 소속 그룹만 가진다.
- 예외 접근은 그룹 중복 소속이 아닌 별도의 권한 정책으로 처리한다.

## 13. 보안 검증 기준

다음 시나리오는 자동화 테스트와 운영 검증에서 반드시 증명해야 한다.

1. `co-a` 장비는 클라이언트가 그룹을 전달하지 않아도 `co-a` 스트림 세션을 생성한다.
2. `co-a` 장비가 `co-b`를 지정하거나 위조해도 `co-b` 스트림을 생성할 수 없다.
3. `co-a` Viewer는 `co-a` 스트림을 조회할 수 있지만 `co-b` 스트림은 조회할 수 없다.
4. `co-a`의 권한 있는 관리자는 `div-1` 스트림을 조회할 수 있다.
5. `div-1` Viewer는 `co-a`, `div-2`, `co-b` 스트림을 조회할 수 없다.
6. 권한 없는 관리자는 select-box에 표시되지 않은 그룹 ID를 직접 전송해도 장비를 배치할 수 없다.
7. 그룹 이동 후 새 송출 세션은 새 그룹에 귀속되며, 기존 토큰은 재사용할 수 없다.

## 14. 최종 설계 원칙

> 장비는 송출 목적지를 알지 못한다. 장비는 UUID와 Credential로 자신의 신원만 증명한다.

> 서버는 등록 장비의 직접 소속 그룹을 기준으로 스트림과 텔레메트리를 귀속시킨다.

> Viewer와 관리자는 역할과 그룹 계층에 따라 자신의 그룹 및 명시적으로 허용된 하위 그룹 데이터만 조회하거나 관리한다.

> 클라이언트가 전달한 그룹명, 스트림명 또는 목적지 정보는 보안 결정의 근거로 사용하지 않는다.

이 설계는 그룹 간 데이터 혼입을 방지하는 동시에, 조직 계층에 따라 상위 그룹이 권한 있는 하위 그룹 스트림을 통합 조회할 수 있는 확장성을 제공한다.

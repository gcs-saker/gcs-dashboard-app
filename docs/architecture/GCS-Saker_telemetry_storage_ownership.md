# Telemetry storage ownership

Auth Policy owns online ingestion, idempotent event history in its Flyway schema's `telemetry_history`, current values in `telemetry_latest`, and PostGIS projections. The schema is `public` in the isolated PostgreSQL fixture and can be `gcs_geo` with the deployment's same-named database role. PostgreSQL is authoritative; Redis and dashboard state are derived caches. REST, internal gRPC and MQTT all reach that owner. Existing mobile requests and response shapes are unchanged.

The backend `LegacyDbTelemetryBulkSink` is a migration-only compatibility consumer. Its history DTO uses `stream_uuid/received_at`, not Auth Policy's `uuid/recorded_at/event_id/group_id` contract. Its SQL now explicitly names `backend_compat.telemetry_history`; it must never insert that DTO into `public.telemetry_history`. Legacy latest values remain in the existing separate `telemetry_realtime` table. Compatibility storage is not an alternative source for online authorization or dashboard reads.

Before enabling this migration-only adapter, apply `deploy/postgres/backend-compat-telemetry.sql` with `psql --set ON_ERROR_STOP=1` using the backend's migration identity. The script is idempotent, uses bounded lock/statement timeouts, and does not rename, copy, truncate or delete canonical data. Existing canonical history requires no backfill. If an old installation contains a different shape under the canonical name, stop and inventory that relation before migration; do not silently reinterpret it.

V31 changes `operational_stream_session_latest` to one row per `(group_id, stream_id)`, choosing the newest heartbeat and then the largest identity. Multiple sessions for a stream remain available in the history table. This corrects the earlier per-session partition without dropping session history or changing the view's column contract.

Removal condition: after the remaining migration-only consumers stop using `LegacyDbTelemetryBulkSink`, remove the compatibility sink and archive its separately owned history. Track that retirement under #917. The compatibility DDL is intentionally not part of Auth Policy's Flyway lifecycle, nor run automatically during production application startup.

## Write authorization and identity ownership (#941)

REST write orchestration is separated from read presentation in `TelemetryWriteController`. Both bearer write routes require the existing `PUBLISH_STREAM` permission and an active group. System administrators and viewers do not receive that permission. A registered device additionally requires active status and an exact primary-group match; ancestor visibility does not grant write access. The credential-authenticated device route and internal gRPC retain their device identity contract. No new mobile fields, MFA steps, addresses or response shapes are introduced.

Registered-device primary membership is authoritative. For unregistered legacy telemetry identifiers, the first accepted group owns the identifier; another group cannot take it over. V37 enforces this persistence invariant on latest and history writes with a transaction-scoped per-identity advisory lock, including simultaneous first claims from independent writers. An approved registered-device group move remains valid without changing its UUID or credential. A rejected write rolls back the whole history/latest transaction before cache invalidation, geofence evaluation, alerts or publication. Historical event-ID backfills do not change identity ownership and are exempt from reauthorization.

The JDBC write boundary limits transaction/query time to three seconds, lock waits to 500 ms and PostgreSQL statement time to two seconds. Storage conflicts use a dedicated SQLSTATE mapped to a redacted typed denial. H2 is a single-writer compatibility fixture; PostgreSQL multi-writer guarantees are tested separately. In-memory writes serialize first claims and use registered-device ownership when configured.

Local reproduction against immutable pre-fix source `4a7dfa95d089c177207df2577a9794bfa57f1895` on 2026-10-15: a viewer write returned HTTP 200, a sibling operator overwrite returned HTTP 200, and group-scoped reads confirmed ownership moved. Only synthetic local fixture data was used. This is not evidence of production exploitation. Physical mobile/Talkback qualification and production rollout remain separate, unperformed checks.
